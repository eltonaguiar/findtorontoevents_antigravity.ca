=========================  Your actual question  =========================

"Is there a government backdoor in Windows, or something a rogue coder quietly built?"

Measured answer: I found no implant. No unsigned driver, no hidden LSA package, no AppInit
hook, no IFEO shim, no WMI subscription, no encoded task, no C2 port, no rogue service, no
unexplained autorun. That is the strongest negative this kind of audit can produce, and it
is a real result - implants usually leave at least one of those footprints.

What I did find is that you do not need a backdoor to have the exposure you were worried
about, because:
  - the firewall is off, so everything listening is reachable,
  - five remote-control products are installed and four are running,
  - five services expose no-auth APIs on 0.0.0.0, two of them running unsigned binaries,
  - SSH accepts passwords and WinRM is open in cleartext.
Any one of those, with a weak or shared credential, is remote desktop control. A state
implant hidden in Windows itself is not something I can confirm or deny from inside the
OS - by definition - and nothing I measured points at one. Treat "documented remote
management left switched on" as the real risk; it is also the one you can fix in ten
minutes.

On "1 API call away": today, from any device on your LAN, a single HTTP request to
:8642 or :8787 reaches an agent gateway. From the internet: only if the router forwards a
port or has UPnP. That is worth checking on the router itself - check its UPnP and port
forwarding list, because the host cannot see it.


=========================  Ranked actions (commands included)  =========================

Do these in order. Nothing below needs a reboot except where noted. None were run by me -
they change how your fleet talks, so you should choose the moment.

1. Firewall on, three profiles:
     netsh advfirewall set allprofiles state on
   Then allow only what you need, scoped to the LAN:
     netsh advfirewall firewall add rule name="fleet LAN" dir=in action=allow ^
       remoteip=192.168.2.0/24 protocol=TCP localport=8787,8788,8642,11434,1234,22
   (Kaspersky, once running, may take over firewall management - do not run both.)

2. SSH: password auth off.
     notepad C:\ProgramData\ssh\sshd_config   ->  PasswordAuthentication no
     Restart-Service sshd

3. Remote access: keep one, stop the rest.
     Get-Service RustDesk,TeamViewer,chromoting,Parsec | Select Name,Status
     Stop-Service <the ones you do not use>; Set-Service <name> -StartupType Manual
   Rotate the RustDesk permanent password; confirm the RustDesk ID is yours.

4. One antivirus, running. Uninstall either Kaspersky or Malwarebytes, then confirm:
     Get-CimInstance -Namespace root\SecurityCenter2 -ClassName AntiVirusProduct

5. WinRM: stop it, or scope the rule to 192.168.2.52.
     Stop-Service WinRM; Set-Service WinRM -StartupType Disabled

6. Turn Secure Boot on (BIOS), then BitLocker on C: and E: - E: holds the keys and the repos.

7. Remove the two SkipUAC tasks if you do not rely on them:
     Unregister-ScheduledTask -TaskName 'ASC_SkipUac_zerou','Driver Booster SkipUAC (zerou)'

8. Enable ScriptBlockLogging (one registry value) so future incidents are readable:
     HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging
       EnableScriptBlockLogging = 1 (DWORD)

9. Router: check UPnP and port forwarding. Nothing on this host should be forwarded.


=========================  Fixes I DID make (reversible)  =========================

The COMS console popups: two Scheduled Tasks were launching powershell.exe with
LogonType=InteractiveToken and Hidden=False, so a console window appeared on your desktop
every 5 minutes (COMS-heartbeat) and every 20 minutes (COMS-watch-50). PowerShell's
-WindowStyle Hidden is not enough - conhost is created before the style applies, which is
the flash you saw. Both now run through wscript.exe (a GUI-subsystem host that allocates no
console at all) via C:\Users\zerou\.coms\watch\launch-hidden.vbs, with Run(...,0,...).
  Verified: both tasks Hidden=True, LastTaskResult=0, and the visible-window count did not
  change when I forced a run (before=0, after=0).
  Backups: C:\Users\zerou\.coms\backup-20261122\*.xml  (restore with schtasks /create /xml)
  Not verified: that the heartbeat publish actually landed on the broker - the task returns
  0 but the script publishes without --retain, so there is nothing to read back. That is a
  property of the script, not a failure.


=========================  What I could NOT check  =========================

Stated so you do not read silence as safety:
  - Router WAN configuration, UPnP mappings, port forwards (not visible from the host).
  - Whether any of the five remote-control tools has an active logged-in session or a
    pending incoming connection (would need their own logs / a packet capture over time).
  - Memory-resident or bootkit-level implants: not detectable with read-only enumeration.
    A rootkit that has hooked the kernel would also hide from the very APIs I used. If you
    want that answered, it needs an offline scan or a second opinion from outside the OS.
  - Firmware/UEFI integrity (no Secure Boot means no measured boot to compare against).
  - Browser extension inventory and Outlook/Teams content (out of scope for this run).
  - Cloud/SaaS side: GitHub token, API keys in dbpasses.txt - I did not test whether any of
    them has leaked or been used from another IP. That is detectably answerable from each
    provider's audit log and is the next audit I would run.
