# Review — PR #794 `feat(finpredict): final_v001 strategy plan + proof-metadata audit steps`

**Reviewer:** Hermes (inspect-wt) · **Date:** 2026-11-15 · **Head reviewed:** `4539b7b9c66`
**Verdict: REQUEST CHANGES** — the docs half is fine; the workflow half cannot do what its name claims, and one of its four instances reports compliance it never tested.

## Verified good

- All four modified workflows parse as YAML (`yaml.safe_load`), each retains its single job and gains exactly one `Validate proof-protocol metadata` step (11/6/5/7 steps respectively).
- Merge against current `main` is clean (`git merge-tree`, no conflicts).
- The proof-metadata key list is a reasonable starting schema: `pf, sharpe, n, wr, oos_pf`.

## Blocking issue — the check can never fail, so it is not a check

Both exit paths leave the step green:

```python
except Exception as e:
    print(f"::warning::Cannot read latest_picks.json: {e}")
    sys.exit(0)                      # unreadable file => PASS
...
if missing_any:
    print("::warning::... incomplete")  # missing keys => PASS (warning only)
```

So the step can only ever produce annotations, never a red run. That is a legitimate choice for *telemetry*, but the PR describes it as "proof-metadata **audit**" / "validation". If it is merged as-is, nobody may cite a green run of these workflows as evidence that picks carry proof metadata — the step would be green with zero metadata present.

**Ask:** either (a) rename these steps to `Telemetry: proof-metadata coverage` so the green means nothing more than "ran", or (b) add a threshold that fails once the pipeline is emitting picks, e.g. `if picks and missing_pct > 0: sys.exit(1)`.

## Blocking issue — dict-shaped payloads are iterated as if they were pick lists

Three of the four steps assume a top-level **list** (`for i, p in enumerate(picks)`). The committed artifacts are **dicts**:

| Artifact | Real shape | Step behaviour (simulated) |
|---|---|---|
| `non_crypto_agent/data/equities_picks.json` | dict, no `picks` key in the committed copy | 0 warnings → prints **"Proof-protocol metadata present on all picks"** |
| `alpha_engine/data/new_strategy_forward_results.json` | dict, keys `generated_at, tracked_strategies, strategy_count, total_active_picks, total_closed_picks, strategies` | **7 warnings** — one per dict *key*, not per pick |
| `incubator/agents/claude_code_01/data/gainer_scores_latest.json` | dict, keys `generated_at, threshold, total_scanned, buy_signals, top, all_scores` | **6 warnings** — same defect |
| `alpha_engine/output/latest_picks.json` | absent in repo (CI artifact) | warn + `exit 0` |

The equities step is the worst of the four: `data.get('picks', [])` on a payload without a `picks` key yields an empty list, the loop body never runs, and the step prints an affirmative compliance claim. **A check that reports success when it examined zero items is precisely the "broken green" failure this repo is trying to eliminate.** Note `non_crypto_agent/*.py:706` does write a `picks` key when the file is regenerated, so the false pass is conditional on the stale/committed shape or an empty pick set — but both are reachable, and an empty pick set should not read as "all picks compliant".

**Ask:** normalise the payload first, e.g. `picks = d if isinstance(d, list) else d.get('picks') or d.get('strategies') or d.get('top') or []`, and print the count examined (`checked N picks`) so a zero-item run is visibly vacuous.

## Non-blocking — schema semantics

- `n` is required per pick. On a per-pick object `n` is ambiguous (sample size of what?). Rename to `n_trades` in the pick schema, or move `n` to strategy level.
- `oos_pf` is a **strategy-level** metric. Requiring it on every pick guarantees permanent warnings until each pick carries a strategy pointer plus a lookup. Prefer `strategy_id` on the pick, with `pf/sharpe/n/wr/oos_pf` resolved from a strategy table.

## Non-blocking — unrelated change bundled in (behavioural risk)

`.github/workflows/alpha-engine-daily-picks.yml` gains:

```yaml
concurrency:
  group: alpha-engine-${{ github.event.inputs.universe || 'default' }}
  cancel-in-progress: true
```

The PR body states it "Preserves origin/main improvements: forward-test concurrency…", but `git show antigravity/main:...` shows **no** `concurrency` block on that file — this is new, not preserved. `cancel-in-progress: true` on a job whose later steps deploy picks over FTP means a second run cancels the first **mid-deploy**, which is how partial site states get created.

**Ask:** separate this into its own PR with a rationale, or land it as `cancel-in-progress: false` (queue instead of kill) if the goal is only to prevent overlap.

## Summary of asks

1. Rename the steps to telemetry, **or** make them able to fail against a threshold.
2. Normalise dict payloads and log the count examined.
3. Move `n`/`oos_pf` to strategy level or rename (`n_trades` + `strategy_id`).
4. Split the `concurrency` change out, or set `cancel-in-progress: false`.

The `WIRED_IN/final_v001/...` documentation and the `AUDIT_FEED_SCHEMA.md` are not reviewed here beyond existence; nothing in them was executed.
