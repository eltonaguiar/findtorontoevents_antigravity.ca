## 3. Action Plan

Ordered by severity. **Nothing below has been applied.**

### 3.1 `audit-dashboard.yml` — widen the cron (highest-impact single fix)

Live wall-clock across the last 6 completed runs is **climbing**:

```
17:14Z  62.5 min (cancelled)
18:16Z  64.7 min
19:14Z  79.7 min
20:14Z  92.3 min
21:14Z  95.5 min
22:14Z 104.0 min
23:15Z 105.9 min
```

CSV average 93.9 min understates it. Live ratio **1.77**, estimated run loss **~43%**.

Current state, verbatim from `git show origin/main:.github/workflows/audit-dashboard.yml`:
```yaml
cron: '10 * * * *'
concurrency:
  group: dashboard-publish
  cancel-in-progress: false
# queue: NOT SET
```

```diff
-    - cron: '10 * * * *'
+    # runtime measured 93.9 min avg (CSV) / 105.9 min latest live. 60-min cadence
+    # silently loses ~43% of fires to pending-slot replacement. Interval now 180 min.
+    - cron: '10 */3 * * *'
```

- **Why O1 (widen interval):** 180 min against a 106-min runtime gives ratio 0.59, and it is the only option that stops pending-slot replacement without creating an unbounded backlog.
- **Not O2 (`queue: max`):** runtime > interval permanently means the queue grows without bound.
- **Not O3 (`cancel-in-progress: true`):** this pipeline writes the dashboard payload; it must not be cut mid-write.
- **Durability caveat:** at the observed growth rate, even `*/3` will be tight within weeks. The durable answer is an **O4 split** — stage the 105-min pipeline into a small shim job (`group: git-push-main`, `cancel-in-progress: false`, `queue: max`) wrapping only the short commit step, never the long scan job. A shared group wrapping 30–105 min jobs gives the whole set 2 slots and makes cancellation *worse*.

If the intent was to bound the workflow, the timeout has to move to the long step or the job — not the push step.

### 3.3 Watchdog — `.github/workflows/gha-watchdog.yml`

The coordinator named this the final deliverable. Requirements derived from what this audit actually found:

1. **Poll `GET /actions/runs?status=queued`, but classify before alarming.** A run is a real queue entry **only if** `GET /actions/runs/<id>/jobs` returns `total_count > 0`. Zero-job `queued` runs are zombie records (52 of them exist right now, up to 100 days old) and **must be skipped**, or the watchdog pages on ghosts forever.
2. **Alert on the silent-loss signature, not on `cancelled` counts.** `cancel-in-progress: false` hides losses: a workflow whose runtime exceeds its cron interval shows *zero* cancellations while dropping 43% of fires. Compare measured runtime (from `Total minutes / Workflow runs`) against the cron interval and alert at **ratio ≥ 1.0**.
3. **Alert on `in_progress` runs exceeding ~2× median runtime.**
4. **Do not alert on runner type/OS or queue depth** — 322/322 hosted Linux, ~1.9 ms mean queue wait, 9 live in-progress. There is no capacity problem.
5. **Bulk-cancel the 52 zombie records** so they stop poisoning the queue count (see §3.5).

### 3.4 Cron interval / jitter hygiene (164 H1 workflows)

- **164 of 312** scheduled workflows have **no `concurrency` block**; **74** are sub-hourly (minute field `*` or `*/N`) and therefore genuinely exposed to overlap and pending-slot replacement.
- **Adding a concurrency block to the 74 is mostly cosmetic.** `cancel-in-progress: false` protects the running run but the pending slot is still a single slot that gets overwritten — a sub-hourly workflow whose runtime approaches its interval still loses runs after you add the block. **Raising the interval is the actual fix**; concurrency is only real protection when runtime is well under the interval.
- **Jitter rule:** never leave a new or edited cron on `:00` or `:30` (or any 5-minute boundary). `0 * * * *` alone appears ~15 times in the H1 set. Use an odd minute: `23 */2 * * *`, not `0 */2 * * *`.
- **Placement rule for `queue:`** — set it at **workflow level**. The claim that job-level concurrency rejects `queue:` was never confirmed; treat workflow level as the safe default.
- **Shared group names are not automatically a bug.** A shared literal group (`git-push-main`) is exactly the O4 serialization mechanism and the repo already uses it (`dynamic-alpha-engine-push`). The bug is a *generic* name shared by unrelated long runtimes — that collapses N workflows into 2 slots and causes cross-workflow cancellation.

## 4. Why the 97–98% failure alarm was false

The worst offenders — `live_trading*` (98.3%), `picks_dispatch` (98.4%), `autonomous_trading` (98.0%), `self_optimizing_trading` (98.0%), `market_beating` (97.1%), `forward_test` (98.3%) — are **push/dispatch-triggered, not scheduled**. They cannot be cron-inversion victims; there is no cron to invert.

In a high-commit repo every push fires them; the concurrency group holds 1 running + 1 pending, so each subsequent push replaces the pending run. The cancelled runs record `jobs_executed=0` — they never started. No code failed.

The repo documents the mechanism itself: `audit-dashboard.yml` carries a 2026-05-19 note that the `push:` trigger was removed because "push-triggered runs piled into the `dashboard-publish-push` concurrency group faster than the ~35-min job could drain, so GitHub auto-cancelled the intermediate queued runs."

**Fix for that cluster is O4 (serialized push), not cron.** Cron changes do nothing for it.
