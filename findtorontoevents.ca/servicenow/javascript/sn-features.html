server1 · GlideRecord — the query workhorse

Every server-side data operation bottoms out here. Query with the most selective condition first, iterate once, and never fetch rows you won't use.

var gr = new GlideRecord('incident');
gr.addQuery('active', true);
gr.addQuery('assignment_group', 'eng_group_sys_id');
gr.orderByDesc('sys_created_on');
gr.setLimit(50);                       // hard cap — always set one
gr.query();
while (gr.next()) {
  gs.info(gr.getValue('number') + ' — ' + gr.getDisplayValue('state'));
}
Trap: gr.getValue('x') returns the database value; gr.getDisplayValue('x') returns what the UI shows (labels, formatted dates). Mixing them up is the classic "wrong data" bug. For references use gr.getElement('x').getRefRecord() when you need the referenced row itself.
// Writing — prefer update() over multiple setValue+update cycles
gr.setValue('state', 3);
gr.setValue('work_notes', 'Auto-closed by nightly job');
gr.autoSysFields(false);              // don't touch sys_updated_on/by
gr.update();

// Bulk paths beat row loops
gr.setValue('active', false);
gr.updateMultiple();                  // one DB round-trip for the whole query result

Encoded queries are the compact way to express conditions, and they round-trip through URLs and gs.generateURL():

gr.addEncodedQuery('active=true^assignment_groupeng_group^sys_created_on>=2026-01-01 00:00:00');
// From the UI: right-click a filter breadcrumb → Copy sys_id / encoded query

server2 · GlideAggregate — counts and sums in SQL

Never query()+loop to count. GlideAggregate pushes COUNT/SUM/AVG/MIN/MAX into the database and returns one row.

var ga = new GlideAggregate('incident');
ga.addAggregate('COUNT', 'priority');
ga.addQuery('active', true);
ga.groupBy('assignment_group');
ga.query();
while (ga.next()) {
  gs.info(ga.getAggregate('COUNT', 'priority') + ' at priority ' +
          ga.getValue('assignment_group'));
}
Rule of thumb: if your loop only exists to count or total, it should be a GlideAggregate. A getRowCount() after query() still materialises the result set — use setLimit(0)+aggregate instead on big tables.

browserserver3 · GlideAjax — calling server code from the browser

GlideAjax is the sanctioned bridge: a Script Include marked Client callable exposes a GlideScratchpad-free, parameter-driven function to a Client Script.

/* Script Include "HRUtil" — Client callable = true, extends AbstractAjaxProcessor */
var HRUtil = Class.create();
HRUtil.prototype = Object.extendsObject(AbstractAjaxProcessor, {
  getOpenCount: function() {
    var user = this.getParameter('sysparm_user');
    var ga = new GlideAggregate('sc_req_item');
    ga.addAggregate('COUNT');
    ga.addQuery('requested_for', user);
    ga.addQuery('active', true);
    ga.query();
    return ga.next() ? ga.getAggregate('COUNT') : '0';
  },
  type: 'HRUtil'
});
// Client Script (onChange of requested_for)
var ga = new GlideAjax('HRUtil');
ga.addParam('sysparm_user', g_form.getValue('requested_for'));
ga.getXML(function(resp) {
  var n = resp.responseXML.querySelector('answer').textContent;
  g_form.setValue('u_open_count', n);
});
Traps: the Script Include must be Client callable and visible to the calling script's scope (cross-scope needs an sys_api_accessor entry). Return values are strings — there is no object transport; use JSON strings for structured data.

g_scratchpad vs GlideAjax: scratchpad = cheap data the form needs at load. GlideAjax = anything fetched after an interaction. Putting a query behind an onLoad GlideAjax call is how forms get slow.

browser5 · Client Scripts — four types, one job each

TypeFiresUse for
onLoadForm loadsInitial tweaks: default visibility, scratchpad reads
onChangeA field changesDependent-field logic (always declare the field)
onSubmitBefore saveValidation; action.setAbortAction(true) to block
Cell EditList-cell editQuick list validations (rare)
function onChange(control, oldValue, newValue, isLoading) {
  if (isLoading || newValue === '') return;
  if (newValue === 'hardware') {
    g_form.setMandatory('short_description', true);
    g_form.addInfoMessage('Hardware requests need a model number.');
  } else {
    g_form.setMandatory('short_description', false);
  }
}
Rule: if the logic protects data (must hold for API/import too), it belongs in a Business Rule or UI Policy — a client script only guards the form it runs on.

browser6 · UI Policies & UI Actions — declarative first

Before writing any Client Script, check whether a UI Policy already does it. UI Policies run on every form type, survive table changes, and their UI Policy Actions set values / visibility / mandatory / readonly without code. Script include "true" expressions cover the conditional part.

// UI Policy: "Urgent needs a workaround"
// Condition: priority is 1 - Critical
// Actions:     work_around = mandatory, work_around = visible
// No JavaScript written at all.

server7 · Business Rules — server-side truth

WhenTimingNotes
asyncafter update() completesDefault; safe for notifications, logging, integrations
syncinside the transactionCan modify current and abort with current.setAbortAction(true); affects every write path (UI, API, import)
(function executeRule(current, previous) {
  if (current.state.changesTo(6)) {           // → Closed
    gs.eventQueue('incident.closed', current, current.caller, '');
  }
  if (current.priority == 1 && !current.work_around) {
    current.setAbortAction(true);             // block the save (sync rules only)
    gs.addErrorMessage('Critical incidents require a workaround.');
  }
})(current, previous);
Trap: a sync Business Rule that calls current.update() re-enters itself — always guard with current.setWorkflow(false) or a property check, or you get the recursion that fills the logs until the transaction dies.

server8 · Script Actions & Events — decoupled reactions

gs.eventQueue('my_app.approval.stuck', current, current.approver, current.number);

An Event is a name plus optional args; a Script Action subscribes to it (optionally filtered by condition) and runs server JS with event, current, gs in scope. Notifications are Script Actions with an email payload. Events queued on tables that later roll back vanish with the transaction — that's a feature, not a bug.

server9 · Flow Designer — modern orchestration

Flows replaced most Workflow Editor content. JavaScript enters through Script steps and Script Actions (which can be reused across flows):

// Script Action "Score incident" — inputs: priority, impact
(function execute(inputs, outputs) {
  var score = (inputs.priority * 10) + inputs.impact;
  outputs.score = score;
  outputs.is_urgent = score >= 25;
})(inputs, outputs);
  • Trigger = record created/updated, schedule, or app event — no more polling jobs.
  • flow.runScriptAction() lets Flow Designer reuse the same actions from other steps.
  • Ask for sys_id inputs, not records, when a flow might run across tables.

server10 · Scheduled Jobs

// Definition runs on a cron-like schedule; the script body is plain server JS
(function run() {
  var gr = new GlideRecord('sysauto_script');   // "Scheduled Job" record
  // ... nightly maintenance ...
  gs.info('Nightly cleanup complete');
})();

For record-heavy work prefer a **Scheduled Job + Flow** hybrid: the job enqueues, the flow processes with retries and steps you can see. Long loops in a job body hit the transaction time limit — page your work with gs.sleep() sparingly or batch by sys_updated_on windows.

server11 · GlideSystem & GlideDateTime

gs.info('hello ' + gs.getUserName());            // scoped log
gs.warn / gs.error                              // log levels
gs.nil(current.getValue('u_foo'))               // null/empty check (not == '')
gs.getProperty('myapp.limit', '50')             // sys_property with default
gs.addInfoMessage('Saved for ' + current.caller.getDisplayName());

var now = new GlideDateTime();
now.addDaysUTC(-7);
gs.info(now.getDate());                          // GlideDateTime math is UTC-based
var diff = GlideDateTime.subtract(now, new GlideDateTime()).getNumericValue();
Timezone trap: GlideDateTime is UTC; display/local conversions need GlideDateTime.setTZ() or gs.beginningOfNextDay()-style helpers. Never hand-roll date strings for queries — pass GlideDateTime objects into addQuery.

server12 · REST Messages & outbound/inbound APIs

var r = new sn_ws.RESTMessageV2('Weather API', 'get forecast');  // [REST Message][endpoint]
r.setStringParameter('city', 'Toronto');
r.setRequestHeader('Accept', 'application/json');
r.setHttpTimeout(15000);
var resp = r.execute();
if (resp.getStatusCode() == 200) {
  var body = JSON.parse(resp.getBody());
}
  • Outbound: REST Message records hold auth (basic/OAuth2), endpoints, and params — the credential stays out of your script.
  • Inbound: Scripted REST APIs (resources) expose ServiceNow as JSON endpoints — runs in a sn_ws.RESTAPIRequest/RESTAPIResponse pair with real status codes.
  • SOAP still exists via sn_ws.SOAPMessageV2 — same execute/parse shape.

serverbrowser13 · Scoped Apps & cross-scope

  • Everything you write lives in a scope (x_company_myapp). Same-scope code sees everything; cross-scope access needs the app to publish APIs: Script Includes marked Client callable or Accessible from settings, plus application access (tables, client scripts) granted per consuming app.
  • current.update() on a foreign-scope table requires ACLs and scope permission — failures surface as GlideRecord.update() returns false, silently, which is why every write's return value should be checked in scoped code.
  • sys_api_accessor records are the audit trail of who may call what; keep them minimal.

server15 · Testing & debugging

  • ATF (Automated Test Framework): test suites run sn_atf assertions against real tables in a snapshot — every Script Include you write should ship with an ATF test (AssertMandatoryValue, GlideRecord helpers, UI Policy tests).
  • Background Scripts for one-off server runs; always setLimit before query().
  • Debug flags: gs.debug() + the developer panel; Business Rule debug lists each rule's runtime; Flow Designer has its own execution log per run.
  • Logs: System Logs → sys_log; gs.log(msg, 'myapp') tags entries for filtering.
