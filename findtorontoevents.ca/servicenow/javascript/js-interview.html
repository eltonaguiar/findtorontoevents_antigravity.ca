The emoji trap. '😀'.split('').length is 2 — two lone surrogates, not one character. [...'😀'].length is 1. If the problem counts "characters", spread the string; if it counts code units, .length or split('') is actually correct. Read the statement carefully, because LeetCode tests both.

2. Set, Map or plain object — when to use which

StructureReach for it whenKey APIWatch out for
Set✳ You need uniqueness or an O(1) membership test. Dedup, "have I seen this?", two-sum complement lookup. add · has · delete · size No indexing, no ordering guarantees beyond insertion order. size, not length.
Map✳ You want a lookup table with non-string keys, or you care about insertion order. Frequency counts, graph adjacency, memoisation keyed on a tuple. get · set · has · size · keys() Object.keys(map) is [] — entries are not own properties. Use [...map.keys()].
{} Keys are strings, you want JSON.stringify to work, and the problem is small. Still the most common choice in practice. obj[k] · Object.keys · in Keys are coerced to strings; inherits from Object.prototype, so obj['constructor'] is a function, not undefined.
Why Map beats {} for a real lookup table: keys can be any type (including a tuple stringified deliberately), there is no prototype to collide with, insertion order is guaranteed, and .size is O(1). Plain objects win on ergonomics and JSON. Both are average O(1) for get/set — the performance difference is rarely the deciding factor; the semantics are.
Two {} traps that actually fail tests:
  • Prototype collisions. count['constructor'] reads the inherited function instead of undefined, so a test input containing the literal string "constructor" corrupts your counts. Fix: const count = Object.create(null), or use a Map.
  • for...in walks inherited enumerable keys. Object.prototype's built-ins are non-enumerable so they stay hidden — until some library patches the prototype. Object.keys() or for...of are the safe forms.

3. The frequency-count idiom

The single most reusable building block in the medium tier — anagrams, group-anagrams, top-K frequent, longest consecutive sequence, substring-with-concatenation.

// Object version — the default choice
const count = {};
for (const c of s) {
    count[c] = (count[c] || 0) + 1;
}

// Alternative: Map version — when keys are not strings, or you want order
const countMap = new Map();
for (const c of s) {
    countMap.set(c, (countMap.get(c) ?? 0) + 1);
}
Why the || 0 is not optional. A missing key reads as undefined, and undefined + 1 is NaN — not 1. One NaN poisons that bucket permanently, and NaN comparisons are always false, so the bug surfaces far away from its cause. ?? (nullish coalescing) does the same job in the Map form and is slightly more precise, since it only falls back on null/undefined.
