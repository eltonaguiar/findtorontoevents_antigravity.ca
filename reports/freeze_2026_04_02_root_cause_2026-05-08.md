## Smoking gun (read first)

`alpha_engine/data/circuit_breaker_state.json` is checked into the repo with:

```json
{ "level": "HALT",
  "max_picks": 0,
  "min_confidence": 1.0,
  "triggers": ["Loss streak 175 >= 25", "Loss streak 175 >= 15", "Loss streak 175 >= 8"],
  "metrics": {"portfolio_dd_pct": 2.0296, "loss_streak": 175, "daily_pnl_pct": 0.034, "closed_picks_count": 527},
  "timestamp": "2026-03-24T06:08:02.492113+00:00" }
```

- Timestamp `2026-03-24T06:08:02` is **9 days BEFORE** the freeze window began. The state has not been overwritten since.
- `level=HALT, max_picks=0, min_confidence=1.0` is the worst-case row in `LEVEL_ACTIONS` (`alpha_engine/portfolio_circuit_breaker.py:73`).
- `production_scanner.py:3513` does `MAX_ACTIVE_PICKS = min(MAX_ACTIVE_PICKS, _cb_state["max_picks"])`. `min(N, 0) == 0` for any N. **No new active picks → no closures → no WON/LOST writes downstream of `forward_validator.run_generation`.** This is exactly the failure mode that `feedback_circuit_breaker_stale_state_leak.md` (cited 2026-04-27 incident, ~115h alpha_engine_fast lockout) was filed against — and the same file is still in the same broken state today.
- The `level=HALT` branch never resets to GREEN unless `check_circuit_breaker()` is invoked AND DD/streak metrics fall below the `YELLOW` floor (line 168-184). On a state-leak, the file is read but never recomputed (only `production_scanner.py` rewrites it at `circuit_breaker_aggregator.get_unified_breaker_state`), so once a stale HALT is committed to git the next workflow run silently inherits it.

## Circuit-breaker state file findings

Contents reproduced above. **Key observations:**
1. Timestamp `2026-03-24` predates the freeze window. State has not been refreshed in **45 days** (today: 2026-05-08).
2. `loss_streak: 175` is impossible for a healthy system — that is the value `_compute_recent_loss_streak()` produces only when `closed_picks.json` had a long contiguous run of `LOST` rows AND the streak iterator never broke. This is exactly the symptom called out in `feedback_phantom_halt_alert_bug.md` ("`_daily_loss` summed realized PnL from terminal-status rows, false HALT on -60.27%/271 vs reality -7.66%/151").
3. `closed_picks_count: 527` is far below today's true count (`closed_picks.json` was 34,860 lines after `6155c1cbf8d` on 2026-04-01). The breaker computed against an old/empty `closed_picks.json` and persisted **only the bad verdict, not the data**.
4. The git-checked-in state file is loaded by every workflow that calls `production_scanner` or `circuit_breaker_aggregator.get_unified_breaker_state`. Until something forcibly recomputes AND overwrites the file, every cron inherits HALT.

This is a **textbook stale-state leak across deploys** — and the same `feedback_circuit_breaker_stale_state_leak.md` fix (lock file + freshness TTL) was scoped for the 2026-04-27 incident but not applied to the **older** 2026-03-24 leak.

## 3 most-likely root-cause candidates

### Candidate A — Stale `circuit_breaker_state.json` HALT persisted into git, max_picks=0 cascades through every cron *(highest probability)*
**Evidence:**
- File contents at `alpha_engine/data/circuit_breaker_state.json` show `level: HALT, max_picks: 0, timestamp: 2026-03-24T06:08`.
- `production_scanner.py:3513` does `min(MAX_ACTIVE_PICKS, _cb_state["max_picks"])` → 0.
- `forward_validator.py:1292` (the only WON/LOST writer in `run_generation`) is downstream of pick generation. No new picks → no closures → no WON/LOST → MySQL sync flatlines on `bt_backtest_trades`.
- Matches `feedback_circuit_breaker_stale_state_leak.md` pattern exactly (cited at 2026-04-27 for ~115h lockout). The 2026-03-24 leak is older and was never caught.
- Explains all 5 broken pipelines: forward-validator (no closures) → algorithm_rolling_perf (computed from forward-validator output) → consensus resolver (stops getting fresh closes) → lm_signals expire-cron (existing-picks cleanup runs but `outcome_resolver` short-circuits on locked breaker) → discord signal_tier (downstream tier classifier reads from forward-validator stats which are empty).

**1-line fix:** delete `alpha_engine/data/circuit_breaker_state.json` (let `check_circuit_breaker()` recompute fresh) and add `if (now - state.timestamp) > 6h: ignore` freshness guard at `circuit_breaker_aggregator.get_unified_breaker_state` per `feedback_circuit_breaker_stale_state_leak.md`.

### Candidate B — 2026-04-04 `79aec7d7356` removed `mysql_fetch_closed_non_crypto` (re-introduced one day earlier in `2c0c0060735`), breaking the closed-pick MySQL backfill pathway *(medium probability)*
**Evidence:**
- `2c0c0060735` (2026-04-03) ADDED `mysql_fetch_closed_non_crypto()` to `audit_trail/mysql_client.py` to pull closed equity/forex/commodity/ETF trades from `ejaguiar1_stocks.trading_picks`.
- `79aec7d7356` (2026-04-04, +24h later) called it "unused dead code" and DELETED it. If any downstream caller — including the `at_consensus_picks` resolver or `algorithm_rolling_perf` writer — was wired through this function, the writer would silently no-op (return None / empty list) on every cycle. Time-travel timestamps (`closed_at < generated_at` in `at_consensus_picks`) are exactly the symptom you'd expect when a closed-pick fetch returns stale fixture rows whose `generated_at` was last touched after `closed_at`.
- The same window (`2026-04-04`) saw `109bbc50f9d` "heal_null_exit_prices_non_crypto" — clear evidence the non-crypto resolver chain was unstable.

**1-line fix:** revert `79aec7d7356` (re-add `mysql_fetch_closed_non_crypto` in `audit_trail/mysql_client.py`) OR confirm via grep that no caller exists; if confirmed, the bug is elsewhere.

### Candidate C — 2026-04-02 `5a6112736c4` "reset C (stale LONGs)" silently truncated/recreated `closed_picks.json` and the resolver chain hasn't reconverged *(lower probability, but worth eliminating)*
**Evidence:**
- That commit touched `production_scanner.py:57`, rewrote `dashboard_payload.json` (125,346 lines diff), and reset stale LONGs. Coincides exactly with the 2026-04-02 freeze date.
- If the reset truncated `closed_picks.json` to 527 rows (matching `circuit_breaker_state.json::metrics.closed_picks_count: 527`), then the breaker recomputed loss_streak against a tiny dataset where 175 contiguous LOSTs were possible (because the dataset only had ~527 rows total → could be a single bad strategy), tripped HALT, and locked itself.
- The `closed_picks_count: 527` in the state file is dramatically below today's 34,860 — strong evidence of a one-time truncation event aligning with `5a6112736c4`.

**1-line fix:** restore `closed_picks.json` from pre-2026-04-02 backup OR force-recompute `circuit_breaker_state.json` from current full dataset before re-deploying any cron.
