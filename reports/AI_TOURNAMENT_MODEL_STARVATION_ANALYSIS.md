# AI Tournament Model Starvation + GitHub Actions Analysis

## Executive Summary

The AI Tournament Pipeline has **23 registered models** in `config/model_persona_mapping.json`, but only **3 models** (`deepseek_v4`, `grok3`, `cerebras_llama4`) are producing actual tournament-grade picks in daily data. The remaining 20 models are invisible ghosts — declared in config but contributing zero picks to the leaderboard or dashboard. This severely undermines the tournament's purpose of comparing many AIs head-to-head.

**Key insight:** Coverage fallback DID work on May 23-25 (ring_261T jumped from 0→28→140 picks), proving the mechanism can work for all 23 models. But it stopped working after API keys were partially configured — models that got any key became "primary" producers and the fallback logic doesn't kick in for them, while models with NO keys get silent-skipped entirely.

### Root Causes (Layered)

#### CAUSE 1: `already_generated()` blocks forced refresh
```python
def already_generated() -> bool:
    if FORCE_REGENERATE: return False
    path = pick_out_path()
    if path.exists():
        data = json.loads(path.read_text())
        if isinstance(data, list) and len(data) > 0:
            print(f"[populate] Today's picks already exist ({len(data)} picks)")
            return True  # ← STOPS THE PIPELINE BEFORE IT EVEN RUNS
    return False
```
If yesterday's picks exist and `FORCE_REGENERATE` isn't set, the pipeline returns immediately without running ANY model calls — including models that haven't participated yet.

#### CAUSE 2: Silent-skip pattern for missing API keys
In `try_prompt_model()`:
```python
if not api_key:
    print(f"  [skip] {label}: missing {api_key_env}")
    return [], "missing_api_key"
```
This returns empty picks with status `"missing_api_key"`. The coverage fallback code checks:
```python
elif COVERAGE_FALLBACK_ENABLED:
    fallback = generate_assignment_fallback_picks(...)
    all_picks.extend(fallback)
```
But this only fires IF the assignment was attempted (persona loop runs). When `already_generated()` short-circuits the entire function, NO assignments are attempted at all.

#### CAUSE 3: Partial API key configuration creates uneven participation
The GitHub Actions workflow sets env vars for 23 potential providers, but in practice only 3-4 API keys are consistently available in CI secrets:
- `DEEPSEEK_API_KEY` ✅ (always set)
- `XAI_API_KEY` ✅ (always set)
- `CEREBRAS_API_KEY` ✅ (usually set, sometimes falls back to CEREBRAS_API_KEY_FREE)

Others may be partially set (GPT-4o-mini uses OPENAI_API_KEY which might be set sometimes):
- `ANTHROPIC_API_KEY` → cursor_agent (appeared May 21, disappeared later?)
- `OPENROUTER_API_KEY` → ring_261T (appeared May 23, dropped off May 25)

When a subset of models starts working, they dominate the output volume, making the problem less visible internally — but the tournament becomes biased toward just those 3 models.

#### CAUSE 4: Carry-forward obscures missing models
```python
existing_open = [p for p in existing_picks if p.get("status") == "OPEN"]
for ep in existing_open:
    if (ep["model_id"], ep["symbol"]) not in existing_ids:
        all_picks.append(ep)
```
Open positions from previous days are carried forward, making it appear as though those models are still active when in reality no new picks are being generated by them.

### What Needs to Change

1. **Always run the full model fleet** — never skip based on yesterday's picks
2. **Mandatory coverage fallback** — every configured model must produce at least one pick per session, even if it's synthetic/fallback
3. **Visibility dashboard** — the tournament page should explicitly show "N/M models produced API picks today, M-N used coverage fallback"
4. **API key rotation monitoring** — track which provider keys expire and alert
