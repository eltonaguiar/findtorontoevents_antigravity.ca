## 2. Aggregator mechanics — why PF=103 on holdout is NOT look-ahead

Aggregator: `tools/audit_pick_funnel/top_edges.py` (413 lines). It is a post-hoc binner:

- Pulls 90d of closed `picks` (`fetch_picks(conn, 90)` at line 293).
- Tags each pick with `{trust, conf, rr, fam, dir, score_dec, source}` (line 105-115).
- Sorts each asset class chronologically by `closed_at` or `created_at` (line 167).
- Splits 60/40 by **cell-row ordering within each class** (line 168). Train = first 60%, holdout = last 40%.
- Enumerates C(7,3)+C(7,4)=70 dimension combos, scores cell-level PF over realized `pnl_pct` (line 131-143).

**This aggregator cannot leak the future into a feature** because it does not compute features. It bins realized outcomes by tags that were stamped on the pick **at creation time**. The only way an artificial PF can appear here is via:

- (a) **A pick row whose stored `pnl_pct` is itself wrong** (resolver bug, sign-flip, mislabel). M-067 + the 2026-04-28 resolver fix already addressed the worst of these; an active PR #143/#134/#162 is closing remaining PnL convention drift.
- (b) **Small-sample noise amplified by chronological tag concentration.** Confirmed mechanism for the FOREX cell:

> `score_dec=S20` is the band where `elite_score` rounds to the 20s (i.e. score in [20, 30)). This band became populated only late in the 90d window (likely a scoring-model rollout). Train half: 5 rows. Holdout half: 245 rows. With FOREX PnLs already in tiny percentage points (most `cta_replicator` losses are −0.002 to −0.011, most wins +0.008 to +0.012), one excluded outlier loss (e.g. the USDJPY=X −0.463 row sitting in `cta_replicator` not in this cell's `multi_asset_copytrader` source band) inflates PF to triple digits. Type-I error from sparse early data + asymmetric PnL filtering.

Live DB cross-check (`picks` table, 90d, FOREX):

```
multi_asset_copytrader: n=709, WONs=115, gross_win=0.68, gross_loss=3.01  → source-level PF=0.226
cta_replicator:         n=184, WONs=106, gross_win=0.34, gross_loss=0.63  → source-level PF=0.540
alpha_engine:           n=50,  WONs=16,  gross_win=0.11, gross_loss=0.17  → source-level PF=0.647
```

**Source-level PF is sub-1.0 across every FOREX source.** The cell-level PF=85 is therefore a slicing artifact, not a real edge.

Deepseek's section 2 (consult MD) concurs: *"the extreme holdout PF is a type-I error from sparse early data + asymmetric PnL filtering, not evidence of look-ahead in the aggregator itself."*

## 3. Real look-ahead Deepseek flagged (separate bug, follow-up)

Deepseek's section 1 identified a genuine look-ahead in `alpha_engine/feature_populator.py`:

> `fetch_klines()` (line 145–175) requests `limit=200` bars from Binance with no filter for the currently-open (incomplete) bar. The most recent kline returned by Binance is **the live bar** whose `close` is the current market price, not the close of a finalized period. Technical features computed in `compute_technical_features()` use `closes[-1]` (the latest "close"), so the feature value at entry-time peeks at intra-bar price action that has not yet finalized.

**Spot-verify:** I read `feature_populator.py:145-175` and `_extract_ohlcv` at line 178-190. Confirmed: there is no `is_closed` filter. Binance kline schema does include `close_time` (index 6) which can be compared to `now` to detect the unclosed bar, but the code does not use it.

**Impact:** This is a *scoring* look-ahead, not an *outcome* look-ahead — it inflates feature predictive power at signal-generation time but does NOT cause the PF=85 artifact in `top_edges_per_class.json`. The latter uses realized `pnl_pct` post-resolution.

**Recommended follow-up (NOT in this PR):** in `fetch_klines()`, drop the last kline if `now_ms < klines[-1][6]` (close_time). This is a one-line fix but needs a smoke test against every caller (`feature_populator`, ML training paths, `ml_crypto_predictor`). File a separate incident: `INCIDENT_CRYPTO_3_feature_populator_live_bar_lookahead`.

## 4. Walk-forward gate proposal (for adoption in a follow-up code PR)

Deepseek's section 3 pseudo-code, refined:

```python
# In tools/audit_pick_funnel/top_edges.py, replace the row-order split with:

MIN_TRAIN_N = 30
MIN_HOLDOUT_N = 30
MIN_HOLDOUT_PF = 1.2
MIN_HOLDOUT_WR_SHRUNK = 0.50

EMBARGO_BY_CLASS = {
    "CRYPTO":    timedelta(days=1),   # short holds
    "FOREX":     timedelta(days=3),
    "EQUITY":    timedelta(days=3),
    "COMMODITY": timedelta(days=3),
    "ETF":       timedelta(days=3),
    "BOND":      timedelta(days=7),   # longer holds
}

def walk_forward_admissible(cell_rows, asset_class):
    rows = sorted(cell_rows, key=lambda r: r["_ts"])
    n = len(rows)
    split_idx = int(n * 0.6)
    train = rows[:split_idx]
    holdout = rows[split_idx:]

    if not train or not holdout:
        return None  # SKIP

    max_train_ts = max(r["_ts"] for r in train)
    embargo = EMBARGO_BY_CLASS.get(asset_class, timedelta(days=3))
    holdout = [r for r in holdout if r["_ts"] >= max_train_ts + embargo.total_seconds()]

    if len(train) < MIN_TRAIN_N or len(holdout) < MIN_HOLDOUT_N:
        return {"status": "SMALL_SAMPLE", "train_n": len(train), "holdout_n": len(holdout)}

    h_pf = profit_factor([r["_pnl"] for r in holdout])
    h_wins = sum(1 for r in holdout if r["_won"])
    h_wr_shrunk = bayes_wr(h_wins, len(holdout))

    bonf_pass = ...  # existing z-score check

    if h_pf >= MIN_HOLDOUT_PF and h_wr_shrunk >= MIN_HOLDOUT_WR_SHRUNK and bonf_pass:
        return {"status": "PASS"}
    return {"status": "AWAITING_WALK_FORWARD"}
```

Rationale for thresholds (per Deepseek + sanity check):

- `MIN_TRAIN_N=30`, `MIN_HOLDOUT_N=30`: binomial CLT regime; below this, single outliers can dominate PF.
- `MIN_HOLDOUT_PF=1.2`: realistic post-slippage edge floor; PF=1.2 ≈ break-even after 5–7bp slippage on FOREX, 10bp on EQUITY.
- `MIN_HOLDOUT_WR_SHRUNK=0.50`: shrunk WR keeps low-n cells from passing on a streak; 0.50 is break-even at 1:1 R:R (paired with PF≥1.2 it is conservative).
- Embargo: prevents the holdout from including picks whose hold period overlaps with the train tail's hold period (multi-day position correlation).
