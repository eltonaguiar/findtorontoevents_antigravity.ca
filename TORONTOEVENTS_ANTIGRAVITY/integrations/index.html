1.CI/CD backbone — GitHub Actions

The entire automation layer runs on GitHub Actions self-hosted/unified runners. Nothing depends on host crons (the shared hosting provider doesn't support them), so every scheduled job is a workflow in .github/workflows/.

Trigger mix & cadence

  • Every 15 min — sports odds anchors, pick funnels
  • Every 30–60 min — dashboard pipeline, DB freshness guardian
  • Every 2–6 h — scanners, top-movies refresh, UEPS picks
  • Daily — event scrape (12:00 UTC), TMDB fetches (06:00 & 07:00 UTC), backups, COT/insider landings
  • Weekly / market-hours aligned — validation, retraining, weekday-only equity jobs

Pipeline safety guardrails

  • Concurrency groups (fte-ftp-deploy, dashboard-publish) serialize FTP writes — two runs can never clobber each other's upload.
  • [skip ci] on every generated-data commit → no deploy loops.
  • Conflict-marker + large-file + safe-push guards (assert_no_conflict_markers.sh, safe_push.sh, branch-large-file-dup-guard.yml).
  • Push trigger deliberately removed from the dashboard pipeline (2026-05-19) — hourly cron + manual dispatch only, preventing cancel-cascade waste.

How Discord alert deduplication actually works

A recurring symbol in the alerts channel is expected behavior — every new trading setup on the same symbol is a new pick and gets a new alert. Dedup operates on the pick, not the symbol, in three layers, and a separate cooldown gate throttles short-term re-alerts (layer 4):

1. Duplicate-emission skip (upstream)

The consensus aggregator re-runs every few minutes. Before recording a pick it checks at_consensus_picks and skips only when an OPEN pick already exists with the same symbol + direction and an entry price within 0.5%, emitted in the last 24 h. A re-fire at a different price — or after the previous pick closed — is a genuinely new pick and flows through.

2. At-most-once delivery (the actual send gate)

Each pick row in consensus_tracked carries a discord_sent flag. Senders select only discord_sent = 0 rows, and after a successful post the row is stamped with the flag, Discord message id and timestamp via a race-safe WHERE discord_sent = 0 update. A crashed-run retry or an overlapping pipeline can therefore never double-post the same pick — but the next pick on that symbol posts normally.

3. Immutable notification ledger (audit trail)

Every actual post — PICK_POSTED, TP_HIT, SL_HIT, REVERSAL, POSITION_UPDATE — is appended to at_discord_notifications with the full payload JSON. Its UNIQUE (symbol, direction, event_type, created_at) index (written with INSERT IGNORE) only collapses writes landing in the same second, e.g. a double-log inside one run. History is never deduplicated away: the same symbol accumulates rows over time as it is re-picked and as its TP/SL events resolve.

4. Short-term cooldown — 30 min per symbol+direction

Yes — the FreshPicks quality gate that every Discord sender runs through enforces G1 dedup/throttle: once a pick on symbol + direction is sent, that exact combination cannot re-send for 30 minutes. The cooldown has one deliberate bypass: if the new setup's levels differ (entry, TP or SL changed), it is treated as a genuinely new setup and passes immediately — so only stale re-fires of identical levels are suppressed, not real new signals. Signals also expire after 15 minutes (G6), so a short-term pick must fire inside its window or is dropped. Cooldown state is persisted in a committed gate-state JSON (data/freshpicks_gate_state.json), so it survives across stateless CI runners, and every rejection is auditable in at_discord_gate_log as G1_DEDUP. A global rate cap (max picks per 60-min rolling window, G7) also exists but is currently uncapped at 999 during a testing sprint — was 8.

5.Duplicate prevention & idempotency

Every integration is designed so that running it twice produces the same state as running it once. Re-runs, retries, overlapping crons and manual refreshes are all assumed to happen — and are safe.

A. Natural-key upsert (SQL level)

Every time-series table carries a UNIQUE constraint on its natural key and writes with INSERT … ON DUPLICATE KEY UPDATE. Re-fetching the same day's bar overwrites it in place — it never duplicates.

  • daily_prices → UNIQUE (ticker, trade_date)
  • cftc_cot_weekly → (symbol, report_date)
  • Crypto OHLCV → (symbol, timestamp)

B. External-id as primary key

When an external system has a stable immutable id, we adopt it as the row key, so the same entity can only ever exist once:

  • events_log.event_id — PRIMARY KEY
  • movies.tmdb_id — UNIQUE (with imdb_id as secondary check)
  • trailers.youtube_key — UNIQUE
  • Prediction markets — deduped by market id

C. Content-hash idempotency keys

When no external id exists, we hash a normalized projection of the record. The hash is the primary key:

  • Events: deterministic MD5 key over normalized title/date/venue → re-scraping the same event updates the row instead of inserting a twin.
  • Picks: pick_hash VARCHAR(64) UNIQUE — the same pick emitted by two systems on the same day lands once.

D. Pre-merge fuzzy dedup

The event pipeline additionally normalizes titles (case, punctuation, whitespace) and runs a fuzzy duplicate check before merging sources — so "Pride Parade 2026" from Eventbrite and Ticketmaster collapses into one event, whichever source lands first.

E. Append-only snapshots

Odds anchors write one immutable file per UTC timestamp (data/pinnacle_snapshots/<UTC>.json). Nothing is overwritten, so freshness checks can trust file age — and no two runs can collide on the same artifact.

F. Workflow-level serialization

GitHub Actions concurrency groups (fte-ftp-deploy, dashboard-publish) queue runs instead of cancelling them, so two overlapping pipelines can never publish interleaved state. Run ledgers (event_pulls, at_aggregation_runs via INSERT IGNORE) record found/added/updated counts per run for auditability.

Deep dive — how a movie or TV show can never be added twice

1. The natural key is TMDB's own immutable id. The movies table declares tmdb_id INT UNIQUE. The same id can physically never exist on two rows, no matter which path inserted it.

2. Every ingest path checks before inserting. Before an INSERT, the fetch code does SELECT id, title FROM movies WHERE tmdb_id = ? and, secondarily, by imdb_id (so a title that changed its TMDB entry still resolves to the existing row). If found, it reuses the existing movie_id and only adds missing trailers/thumbnails.

3. Trailers are deduped too. trailers.youtube_key is UNIQUE — if TMDB returns the same YouTube trailer for the trending call, the bulk call, and a manual admin fetch, the row is written once.

The three scheduled TMDB ingestions (MOVIESHOWS2 daily 06:00 UTC, MOVIESHOWS3 daily 07:00 UTC, plus the 6-hourly Top-100 refresh) and the manual admin fetch buttons all converge on that same natural key — which is why the libraries can be re-seeded from scratch without producing duplicates. User-generated rows are equally guarded: watchlists and likes carry UNIQUE (user_id, tmdb_id) composite keys.

The events pipeline follows the same philosophy with a content hash (no global event id exists across Eventbrite/Ticketmaster/Meetup), and the price tables with a composite natural key — same design principle, adapted to what each source makes available.

9.ServiceNow integration playbook

The platform patterns below follow ServiceNow's published guidance (official product docs, cloning/upgrade KB articles and community playbooks). They apply to any ServiceNow estate we integrate with — including this platform's own tooling pages under /servicenow/.

9.1 Anatomy of any integration — the checklist every connector must answer

Identity & ownership

  • Named owner + technical contact per integration
  • Source of truth declared per field (not just per system)
  • Environment map: dev → test → prod, and how config travels (update sets / source control)

Protocol & auth

  • Transport: REST / SOAP / SQL / file / event bus — prefer REST+JSON
  • Auth: OAuth 2.0 client credentials first; mutual TLS or key vault second; no shared passwords
  • Credentials stored in the credential store / secrets manager, never in scripts

Data contract & idempotency

  • Stable external key per record (sys_id mapping table or natural key)
  • Upsert semantics — reruns must not duplicate (same principle as this site's own pipelines)
  • Field mapping + transform versioned with the integration, not in a wiki

Reliability & observability

  • Cadence and allowed window (see freezes below); retry/backoff policy
  • Error queue with replay (integration hub execution log / ECC queue / MID logs)
  • Freshness alerting — a dead integration must page someone, not fail silently
  • Audit trail of sends/receives and a documented rollback path

9.3 Worked examples

Jira ↔ ServiceNow

Recommended: the Jira Spoke (IntegrationHub) + Flow Designer — manage issues, users, stories, sprints and webhooks from flows, in either direction. Use OAuth, declare the source-of-truth per field (e.g. Jira owns sprint state, ServiceNow owns incident state), and reconcile status codes through a lookup — never dual-write the same field from both sides. No IntegrationHub subscription? Fall back to a scripted REST integration (you own retries) or a Store connector. At high volumes, prefer scheduled batch flows over per-record triggers to control transaction consumption.

SCCM ↔ ServiceNow (CMDB)

Recommended: the Service Graph Connector for Microsoft SCCM through a MID Server — per official docs it maps and inserts SCCM data using the Robust Transform Engine (RTE) and the Identification & Reconciliation Engine (IRE). Raw REST straight into cmdb_ci_computer is the classic anti-pattern: it skips identification rules and floods the CMDB with duplicate CIs.

9.4 CMDB integrations & the IRE engine

How IRE runs (and how to make it run)

IRE fires automatically whenever a payload arrives through an IRE-aware pipeline: Service Graph Connectors, Discovery, IntegrationHub CMDB actions, or a direct call to the Identification & Reconciliation API from a script/flow. Identification matches the CI (rules + coalesce attributes), reconciliation decides which data source may write each attribute (authoritative source ranking). To exercise it deliberately: run identification simulation on a sample payload before enabling a connector, replay runs from Configuration → Identification Logs, and raise logging with the glide.cmdb.logger.source.identification_engine property when debugging.

How to stop IRE (rare — know the levers)

There is no supported platform-wide on/off switch; opting out means not routing data through IRE-aware pipelines. Programmatic: write with plain GlideRecord (ORM writes to CI tables bypass IRE entirely), or land data via a transform map with coalesce fields into a staging table that does not extend cmdb, then promote it later. Non-programmatic: keep the payload off the CMDB class hierarchy (a non-CI table inherits no identification rules), and use the IRE properties as behavioral kill-switches — glide.class.upgrade.enabled / glide.class.downgrade.enabled / glide.class.switch.enabled (block reclassification, IRE raises a task instead), glide.identification_engine.skip_duplicates (error instead of auto-merge), glide.required.attribute.enabled. Bypassing IRE trades duplicate-safety for speed — never do it on the production CMDB.

7.Secrets & security posture

How credentials are handled

  • GitHub Actions secrets hold FTP credentials, the TMDB sync gate, PATs and provider API keys. Workflow logs are sanitized so tokens never appear in output.
  • Server environment variables hold DB and provider credentials for PHP endpoints — code reads getenv(), never literals.
  • Client-side keys are public-tier by design (read-only market data: Binance public endpoints, TwelveData demo tier). They carry no account authority and cannot place orders or read private data.
  • Inbound HTTP endpoints are key-gated — unauthenticated refresh requests are rejected before any DB write.
  • This page publishes no secrets — only service names, protocol types, env-var names and cadences.

Hardening status

  • ✅ Least-privilege PATs; workflow permissions: blocks scoped per workflow (e.g. contents: write only where data commits are needed).
  • ✅ No pull_request_target code execution on fork PRs.
  • ✅ TLS in transit for all REST calls; FTPS for hosting deploys.

8.Freshness & reliability monitoring

  • DB freshness guardian (db-freshness-guardian.yml, hourly) — fails the build if live picks, resolver output or backtest tables go stale.
  • Asset-class freshness watchdog — flags any asset class whose last data point falls outside its expected cadence.
  • Actions failure guardian — surfaces workflows with no subsequent successful run, so a silently-broken integration can't stay hidden.
  • Cross-DB consistency audit (daily) — strategy keys must agree across the 9 databases.
  • Backup verification — periodic restore-check of database backups, reported by email.
  • Per-run ledgers — event_pulls and aggregation-run tables record found/added/updated counts per run, making every integration's behavior auditable after the fact.
