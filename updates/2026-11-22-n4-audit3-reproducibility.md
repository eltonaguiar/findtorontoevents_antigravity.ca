# N4 — audit3 ledger reproducibility: the rows digest points at a file that never existed

Date: 2026-11-22
Scope: diagnose the digest contract, regenerate the canonical rows sidecar, verify.
No commits, no pushes (orchestrator commits).

## Verdict

**audit3 is NOT reproducible.** The published rows digest cannot be re-derived from any
rows file that exists, and there is more than one published value. The ledger's
per-class figures were scored from a rows sidecar that has never been committed to the
repository, so they cannot be re-checked from the tree. Documenting the contract is the
honest outcome; the ledger has been relabelled `digest_stale` rather than re-blessed
with a fresh hash.

## 1. The contract

### Target path

- Filename constant: [`resolved_closed_view.py`](alpha_engine/resolved_closed_view.py:42)
  `ROWS_FILENAME = "resolved_closed_picks_net.json"`
- Writer: [`dashboard_generator.py`](audit_trail/dashboard_generator.py:14914)

  ```python
  _canonical_path = (
      ROOT / "audit_dashboard" / "data" / resolved_closed_picks_net["rows_file"]
  )
  ...
  _write_canonical_view(_canonical_path, _canonical_view)
  ```

  `ROOT` is the repo root; the path is a **hardcoded default** derived from
  `rows_file` in the payload block. No env var, no CLI arg. The URL the audit3
  workflow fetches is `https://findtorontoevents.ca/audit/data/resolved_closed_picks_net.json`
  ([`audit3-ledger.yml`](.github/workflows/audit3-ledger.yml:68)).
- The file is **not in the repository and never has been**:
  `git log --all -- audit_dashboard/data/resolved_closed_picks_net.json` is empty.
  It is regenerated by the dashboard build and served, not committed.

The brief quoted `ed25b59c52a4…`; that is the **payload block** value, not the ledger's.
The ledger (the file audit3 publishes) carries `63609da549a7…`, reproduced verbatim in

So even the "published digest" is ambiguous: two surfaces, two different values, both
claiming `mode: canonical` / `loaded_from_sidecar: true`, for two different row counts.

### What is hashed

**Not the file bytes.** A canonical JSON serialisation of the `rows` list only:

[`resolved_closed_view.py`](alpha_engine/resolved_closed_view.py:323)

```python
rows.sort(key=lambda r: r.get("closed_at") or "")
blobs = json.dumps(rows, sort_keys=True, separators=(",", ":")).encode("utf-8")
```

[`resolved_closed_view.py`](alpha_engine/resolved_closed_view.py:344)

```python
"rows_sha256": hashlib.sha256(blobs).hexdigest(),
```

i.e. sorted keys, compact separators, UTF-8, no trailing newline, rows sorted by
`closed_at`. The sidecar file on disk is written differently
([`resolved_closed_view.py`](alpha_engine/resolved_closed_view.py:425):
`json.dump(view, fh, separators=(",", ":"))` + `"\n"`), so **`sha256sum` of the file is
expected to differ from `rows_sha256`** — that is by design, not a defect.

### Post-write or frozen expectation?

**Post-write.** The digest is computed from the rows in the same `build_view()` call that
produces them, and the payload carries it. `load_sidecar()`
([`resolved_closed_view.py`](alpha_engine/resolved_closed_view.py:459)) only *compares*
the payload block's value against the sidecar's stored value, and returns `None` on
mismatch. Nothing asserts a historical constant. Consequence: every rerun legitimately
changes the digest, which is exactly why an unverifiable published digest is a weak
anchor.

### Why this is not just "the data moved on"

The three published values and the regenerated one disagree with each other *and* with
the row counts they claim to describe:

| Digest | Claimed rows |
|---|---|
| `63609da5…` (ledger) | 8,769 |
| `ed25b59c…` (payload block) | 8,827 |
| `e346e65f…` (live sidecar) | 8,816 |
| `c0942d9e…` (regenerated, this run) | 10,968 |

internally (`sha256(canonical(rows)) == rows_sha256` for its 8,816 rows), does not match
either digest recorded in the repo. The digest is a moving target recomputed on every
build; any copy of it in a ledger or a document is stale the moment the dashboard
rebuilds.

## 4. What would make audit3 reproducible

1. Commit the rows sidecar (or publish it as a versioned artifact) alongside the ledger,
   so a digest can be checked against the rows it describes. Today neither exists in
   the tree.
2. Or drop the digest from the ledger and record only the row count + provenance, since
   a digest over a file that is regenerated every build and never retained is not a
   reproducible anchor.
3. Keep exactly one canonical definition of the rows: the payload block (8,827) and the
   ledger (8,769) currently disagree on the denominator while both claim `mode: canonical`.
