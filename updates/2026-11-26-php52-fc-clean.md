# `/fc` is PHP 5.2-clean: all 27 baselined hits fixed, baseline removed (2026-11-26)

## Situation

The widened gate (PR #1206) covered `favcreators/docs` — deployed as
`findtorontoevents.ca/fc` — with 27 known hits accepted through
`tools/php52_baseline.json`. Those are real faults, not noise: 50webs runs
**PHP 5.2.17**, where short array syntax is a **parse error**, so any file using
`[...]` cannot execute at all.

## Two scanner false-positive classes found while working through them

1. **Inline JavaScript.** `google_auth.php` emits jQuery that calls
   `.then(function(r) {...})`. The scanner matched whole files, so 4 of the 27 were
   HTML/JS, not PHP. The scanner now blanks everything outside `<?php ... ?>`
   (`php_regions()`) before matching.
2. (Already fixed in #1206) markdown inside PHP strings.

After the PHP-region fix the real count was **23**.

## The 23 fixes

| Rule | Sites | Change |
|---|---|---|
| `http-response-code` (5.4) | 10, across `creator_news_api`, `creator_news_creators`, `crypto_picks_api`, `discord_interactions_backend`, `discord_unlink` ×3, `get_creator_post_counts`, `google_verify`, `thumbnail_proxy` | guarded `function_exists` call **plus** the raw `HTTP/1.1` status line |
| `short-array` (5.4) | 10, in `batch_update_streamer_last_seen` ×7, `ft_test_db` ×2, `ensure_tables` ×1 | converted to `array(...)`, including two multi-line literals |
| `null-coalesce` (7.0) | 3, all in `batch_update_streamer_last_seen` | `isset($x) ? $x : $default` |

`batch_update_streamer_last_seen.php` was the worst offender — it used `??` **and**
short arrays, so on 5.2 it died at parse time regardless of input.

## Baseline removed

`tools/php52_baseline.json` is deleted and the workflow no longer references it, so
the gate is now absolute: **any** finding in **any** of the three trees fails CI.

## Verification

- `python3 tools/php52_compat_lint.py` → `105 file(s) scanned, 0 new finding(s), 0 baselined`, exit 0.
- `php -l` clean on all 11 edited files.
- `python3 -m pytest tests/test_php52_compat_lint.py -q` → **11 passed**, including
  `test_full_repository_scan_is_clean`, which now asserts the baseline file does not
  exist before running the scan.

## Two false negatives found by checking the live host, not the lint

After the 23 fixes the gate reported 0 findings, yet `POST /fc/api/batch_update_streamer_last_seen.php`
still returned **HTTP 200 with `<b>Parse error</b>: unexpected '['`**. The scanner had
two blind spots, both now covered:

1. **Empty short arrays.** The rule anchored on the first element
   (`[` followed by a quote/`$`/digit), so `$results = [];` and `'tables' => []`
   never matched. The class now includes `]`.
2. **Dereferencing a call result** — `$row = $obj->fetch_assoc()['count']` is 5.4+
   and is `unexpected '['` on 5.2. New rule `call-array-deref`.

Both sites were fixed (`$results = array();`, `'tables' => array(),`, and the count
assigned via a temporary) and redeployed. Live verification afterwards:

- `POST {}` → **400** `{"ok":false,"error":"Invalid JSON input..."}`
- `POST {"updates":[]}` → **200** `{"ok":true,"processed":0,"results":[]}`
- `GET ft_test_db.php` → **200**, no parse error

Lesson: a clean lint result is not evidence a file runs. The only proof is a request
against the host.
