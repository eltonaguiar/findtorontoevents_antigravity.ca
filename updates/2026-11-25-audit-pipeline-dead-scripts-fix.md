**Branch:** `fix/audit-pipeline-dead-scripts-2026-11-25`

## What was broken

### P0 — the diagnostics step called a script that does not exist

`.github/workflows/ai-tournament-pipeline.yml` invoked:

```
python tools/ai_tournament/generate_diagnostics.py || echo "::warning title=diagnostics::Diagnostics generation failed"
```

`tools/ai_tournament/generate_diagnostics.py` **has never existed**. The real
script is `tools/ai_tournament/build_model_diagnostics.py`.

The failure was invisible because two separate mechanisms both swallowed it:

1. `|| echo "::warning ..."` turns a non-zero exit into exit 0.
2. The enclosing step carries `continue-on-error: true`, so even a hard failure
   could not fail the job.

Net effect: `audit_dashboard/data/ai_tournament_model_diagnostics.json` was never
regenerated while CI stayed green, leaving the fleet-status panel on
`/audit/ai-tournament.html` frozen.

### P1 — one credential served two accounts on two hosts

`deploy_instrumented_audit.py` logged into 50webs (`ejaguiar1`) **and** into
`162.210.101.36` as `findtoro`, using the **same** `os.getenv('FTP_PASS')` for
both. `162.210.101.36` is the host identified as the origin of the 2026-11-25
phishing kit. One environment variable therefore unlocked two unrelated servers,
so a leaked `FTP_PASS` was directly replayable against the phishing-kit host.

The same pairing was documented as an instruction in `.agent/workflows/deploy.md`.

The script also wrote `audit_dashboard/index.html` directly, which `CLAUDE.md`
forbids (that file is generated by the dashboard pipeline, not hand-deployed).

### P2 — four deploy scripts referenced source files that do not exist

| Script | Missing sources |
|---|---|
| `tools/deploy_to_altsite.py` | 25, incl. `index.html`, `api/get-movies.php`, `api/login.php` |
| `tools/deploy_movieshows3.py` | 15 |
| `tools/deploy_movieshows2.py` | 7 |
| `tools/gen_deploy_html.py` | 1 (`index.html`) |

`deploy_to_altsite.py:399-400` proves it `open()`s those paths, so every run
would raise `FileNotFoundError` after partial uploads. None of the four is
referenced by any workflow, cron, or executable caller — verified by stem grep;
every remaining reference is a self-docstring, a prose mention, or a
non-executable inventory.

### Why `::error` and not a hard failure

The step keeps `continue-on-error: true` because a diagnostics snapshot must not
be able to fail the whole tournament pipeline. Since a non-zero exit can never
fail the job here, the only available lever is *visibility*. `::error` produces a
red annotation in the Actions UI (and in the job summary) while still letting the
rest of the step run, because the `|| echo` keeps the script's exit code at 0.
